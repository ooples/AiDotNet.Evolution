# US-09 — Preserve useful tradeoffs between objectives

As an application developer, I want valid speed/memory/accuracy tradeoffs so that I can select a solution for my deployment constraints.

Implementation is in AiDotNet.Evolution, based on the US-10 integration (PR #86). Validation and publication are pending.

## Acceptance

- Given conflicting objectives and hard constraints, when the optional bounded Pareto archive is used, then only feasible nondominated entries are retained.
- Given different directions, scales and tolerances, when comparing vectors, then explicit fixed definitions control comparison and every declared hard constraint must be reported as zero.
- Given a Pareto run, when snapshotting, querying, selecting, migrating or stopping, then the front remains explicit and scalar Best is only a documented representative.
- Given fixed bounds and reference point, when running equal-call-budget experiments, then hypervolume and individual objectives are reported against scalar-single and capacity-matched scalar-map64 baselines.
- Given an existing scalar consumer, when Pareto is not opted into, then ordering and checkpoint semantics remain unchanged.

## Product contract

Use two or three ordered EvolutionObjectiveDefinition axes and an EvolutionParetoDefinition (capacity 2..1024, exact hard-constraint count 0..64).
Bounds define the admissible objective domain and fixed hypervolume normalization. Out-of-domain or missing values are rejected, never clipped or treated as zero.
Tolerance is an optional normalized loss bin width anchored at the ideal bound. Zero compares raw objective values exactly; nonzero bins provide transitive comparison.
Equal boxes retain the ordinal-smallest genome identity. Hypervolume uses unquantized values and the fixed normalized worst corner (1,...,1).

ParetoArchive retains only feasible candidates. There is no infeasible exploration pool to accidentally promote.
Capacity uses fixed-scale crowding with deterministic identity ties. It retains an online subset, not the exact historical unbounded front; insertion order can matter when pruning.
Duplicate genome identities are not reevaluated into new archive entries.
Snapshots retain objective definitions and validate the front; checkpoints validate definition hashes, capacity, constraint shape, identity keys and nondominance before restoration.

Explicit ParetoEvolutionSelectionPolicy uniformly samples the entire front. ParetoMigrationPolicy sends sparse/extreme tradeoffs around a ring using crowding.
The engine requires these policies for Pareto runs and rejects scalar target quality, scalar global/history pools, and scalar cascade gates.
Early stopping, if enabled, must use ParetoHypervolume: mean retained-front hypervolume across islands, not summed duplicate volume or scalar Best.
Zero minimum improvement still requires a strictly positive gain. A fixed evaluation budget remains available without early stopping.
Best and scalar quality fields remain representative/reporting values. ParetoFront(), BestObjective(name), Hypervolume() and GetParetoDefinition() expose the objective contract explicitly.
The result-level ParetoFront() is a stable, capacity-bounded merge of retained island fronts.

## Example

```csharp
var definition = new EvolutionParetoDefinition(new[] {
    new EvolutionObjectiveDefinition("latency-ms", EvolutionOptimizationDirection.Minimize, 0, 1000),
    new EvolutionObjectiveDefinition("accuracy", EvolutionOptimizationDirection.Maximize, 0, 1)
}, capacity: 64, constraintCount: 1);
var options = new EvolutionEngineOptions { MaxEvaluationAttempts = 1000 };
options.EarlyStopping.PatienceEvaluations = 100;
options.EarlyStopping.Metric = EvolutionEarlyStoppingMetric.ParetoHypervolume;
var engine = new EvolutionEngine<MyGenome>(task, variation,
    _ => new ParetoArchive<MyGenome>(definition), options,
    selection: new ParetoEvolutionSelectionPolicy<MyGenome>(),
    migration: new ParetoMigrationPolicy<MyGenome>());
// Completed evaluations must report objectives in declared order and exactly one zero violation.
var result = await engine.RunAsync(seeds);
var tradeoffs = result.ParetoFront();
```

## Adversarial review and evidence protocol

Review targets: missing constraints, nonfinite/range overflow, nontransitive approximate dominance, identity ties,
dominated high scalar scores, capacity eviction, snapshot semantic loss, corrupted checkpoints,
scalar policy leakage, strict plateau handling, worker/restart reproducibility and weak benchmark comparators.

The authored development campaign uses 24 paired seeds, two competing-quadratic fixtures (two and three objectives),
three policies, 128 charged calls per run, eight identical seeds per comparison, shared constraint handling and mutation.
Every run is replayed with four workers. All terminal evaluations and retained objective vectors are preserved.
Capacity-matched scalar MAP-Elites has the same 64-entry bound; scalar-single is separately labeled as capacity 1.
Metrics include normalized hypervolume, raw objective extrema, retained count, feasible samples, charged calls/cost and descriptive elapsed time.
These are synthetic objective losses, not measured latency/memory or evidence of beating OpenEvolve.
Run: quality harness `--pareto-study <compiled-source-revision> <new-report.json>`.
