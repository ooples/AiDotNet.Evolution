# US-08: Adapt proposal strategies using measured outcomes

Issue [#26](https://github.com/ooples/AiDotNet.Evolution/issues/26). Current implementation is entirely in **AiDotNet.Evolution**, based on US-07 [#78](https://github.com/ooples/AiDotNet.Evolution/pull/78). Historical merged [#51](https://github.com/ooples/AiDotNet.Evolution/pull/51) supplied reusable core guards; its old study and AiDotNet companion are not current integration proof or dependencies.

As a user, I want search to favor productive proposal strategies so that it spends less effort on ineffective mutations.

- [x] **Given** a portfolio of mutation, crossover, restart, local-refinement and consumer-provided LLM operators, **when** outcomes arrive, **then** selection uses valid improvement or archive success per declared proposal-plus-evaluation cost while retaining exploration. `EvolutionCostedPortfolio.Create` wires every arm to one ledger. Backends must aggregate their own model, parsing, repair and refinement work in actual receipts; the evaluator uses that same ledger without double-counting. Real local operators and a scripted-model admission regression exercise this contract without live calls.
- [x] **Given** an operator produced a candidate, **when** evaluation commits, **then** typed credit identifies the operator/configuration, archive outcome and consumed proposal/evaluation costs once. In-process notifications are guarded against failures/reentry; they are not a transactional exactly-once external storage guarantee.
- [x] **Given** adaptive state, **when** a compatible run resumes, **then** learned history, pending attribution, child state and engine-owned random streams restore consistently. Coordinated engine/ledger boundary replay and pending-attribution tests run in this repository. The caller persists the ledger with the corresponding engine checkpoint; the factory does not claim automatic cross-store transactions.
- [x] **Given** the best static preset from development and a uniform-mixture control, **when** adaptation is evaluated, **then** both multiplicity-adjusted held-out lower gain bounds must exceed 0.02 before promotion eligibility. The registered v2 campaign uses the actual engine, 32 development and 512 confirmation seeds, fresh workload instances, and 12 contrasts. No default is changed by this PR.

Scope: actual local numeric/expression/kernel operator comparisons plus scripted-provider accounting, not model-quality superiority, unrestricted code-generation benchmarks or production speedups. Concrete additional operators/models/prompts remain US-13/US-19 scope. No AiDotNet or Tensors change is required.
