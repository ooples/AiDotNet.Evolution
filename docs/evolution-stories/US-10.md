## User story and acceptance criteria

**Priority:** P1. **Owner:** Performance maintainer. **Depends on:** US-01, US-04.

As a .NET developer, I want low orchestration overhead so that the engine remains useful when candidate evaluation is cheap.

- [ ] **Given** pinned hardware and runtime settings, **when** engine operations are benchmarked, **then** throughput, allocations, peak memory, and checkpoint overhead are reported across archive sizes, island counts, and worker counts.
- [ ] **Given** mixed evaluation durations, **when** batch and continuous dispatch are compared, **then** worker utilization and quality versus elapsed time are both reported.
- [ ] **Given** deterministic evaluators and fixed semantic settings, **when** worker count changes, **then** determinism checks pass; continuous-mode comparisons explicitly fix `MaxInFlight`.

These boxes are deliberately **not ticked**. What the campaign does and does not establish, precisely:

| Criterion | Measured | Not established |
| --- | --- | --- |
| Pinned hardware and runtime settings | Per-child CPU mask (one logical processor per physical core, away from CPU 0), processor count, CPU-group binding, tiered compilation off, 1 ms timer resolution, GC mode, and per-attempt foreign CPU load on the pinned processors (flagged above 5%, failing above 25%) | CPU frequency, power plan and thermal state are recorded, not pinned; the host is shared, not reserved; one machine, one OS build, one CPU |
| Throughput, allocations, peak memory, checkpoint overhead | Median with minimum/maximum across three fresh-process repetitions per case, per-operation throughput and managed allocation, process-lifetime peak working set, checkpoint store time, payload bytes and save counts | Native/unmanaged memory, serialization cost inside the checkpoint path, and any release-calibrated threshold |
| "Across archive sizes" | Archive fixtures with 100/1,000/10,000 **occupied** cells and 1/8/32 descriptor dimensions; engine cases with 32/256/4,096 cell **capacity** | Engine cell factors are capacity, not occupancy: across this campaign the 256-cell engine cases ended with between 57 and 233 cells occupied, so engine "archive size" scaling is a capacity contrast |
| "Across island counts" | 1/2/4 islands | Only at one worker, batch dispatch, checkpoints off, cheap evaluation and no migration (`MigrationInterval = 0`); island scaling under parallel workers, continuous dispatch or migration is untested |
| "Across worker counts" | 1/2/4 workers for engine and evaluator-only cases, cheap and mixed durations, both dispatchers, checkpoints on and off | Beyond four workers, and beyond the four pinned logical processors |
| Mixed durations, utilization and quality over time | Genome-determined 0/1/8 ms delays whose **observed** durations are recorded per bucket and validated against the declared schedule, evaluator-slot utilization, and complete quality-versus-elapsed-time curves for both dispatchers | Simulated asynchronous waits are not CPU, GPU or model-provider work; utilization is slot occupancy, not CPU utilization |
| Worker-count determinism | Identical state hashes within fixed dispatch, checkpoint, operator and seed semantics, for both the parent-independent restart proposer and a parent-dependent mutation operator, with `MaxInFlight` fixed at 8 | Determinism across dispatch modes or checkpoint settings, which legitimately differ; and any claim about non-deterministic evaluators |

One authored sphere objective and one fixed seed on one host are diagnostic scaling evidence. Story acceptance also
depends on US-01's representative workloads and US-04/US-12's statistical release gates, which are not in this PR.

Deliverable: a BenchmarkDotNet project outside the shipping package. Engine throughput and resulting-algorithm speedup
are distinct measurements. These local engine profiles do not establish the latter.

## Evidence and verification

[Protocol and reproduction](../../benchmarks/AiDotNet.Evolution.Performance/README.md).
[Complete results and limitations](../../benchmarks/evidence/performance/README.md).
[Committed evidence summary](../../benchmarks/evidence/performance/b6303d6-summary.json), source
`b6303d6208bf8f7a06d0cb9cee483e685ee5e2f2`, verified against the commit compiled into the measured assembly:
47 cases × three fresh-process repetitions, all 141 planned attempts passed, nine worker-determinism groups passed,
plus one retained `contended` attempt that was retried after the host went quiet. Worker comparisons fix dispatch,
checkpoint settings, proposal operator, seed, dimensions, islands, budget and MaxInFlight=8. The 5.2 MB raw report is
published as a release asset with its SHA-256; the committed summary is 425,232 bytes and the published tables
regenerate from it.

Local verification: 78 profiling contract tests, seven applied mutations of the measurement core all killed; all 661
core tests on each of net10.0, net8.0 and net471; successful full solution formatting verification. The profiler
records .NET 10.0.12, Windows build 26200, x64, CPU group/mask, SMT layout, power plan, timer resolution, processor
count, GC mode and runtime controls, and measures both the simulated delays it awaits and the foreign CPU load on its
pinned processors. Only owned child settings change; host frequency, power policy and background load are recorded,
not controlled — 118 of 142 attempts saw more than 5% foreign CPU on this shared workstation. Lifetime peak working
set includes startup/setup/warmup, and is distinct from managed allocation.

The [original 132-attempt campaign](../../benchmarks/evidence/performance/0bed72d-failed-summary.json) remains failed: it
incorrectly grouped checkpoint-on/off runs into the same deterministic comparison. Continuous checkpoint drains change
proposal context and lineage; worker counts do match within each fixed checkpoint setting. It is retained as a compact
record of the two fixed-semantics groups whose state hashes diverged, with its raw report published as a release asset.
The corrected report is a new full run, not a rewrite of the failed result. Checkpoint timing includes queue-drain
effects; batch and continuous saved nine and seven checkpoints per iteration under the same configured interval. The
evidence explicitly discloses this distinction.

Hosted CI and independent review must be evaluated on the pushed head; no approval is claimed by local tests or a
bot status alone. CI now tests profiling contracts, runs isolated smoke on Linux and uploads all raw diagnostics.
These descriptive single-task measurements are not calibrated release thresholds; representative quality/statistics
remain with US-01, US-04 and US-12.
