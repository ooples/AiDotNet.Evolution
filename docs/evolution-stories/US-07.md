# US-07 — measured feature ablations and guarded presets

Issue [#25](https://github.com/ooples/AiDotNet.Evolution/issues/25).
Owner: AiDotNet.Evolution only. This integration builds on current US-06 PR #77;
the v1 pilot in PR #50 is historical, not current confirmation evidence.

As a maintainer, I want feature-removal experiments so that defaults reflect
measured benefits rather than the number of enabled features.

## Given / When / Then

- **Given** equal initial populations, evaluator/proposal caps, workers and elite
  capacity, **when** Uniform, Ratio, Curiosity and Double run, **then** report
  quality, diversity, success, calls, CPU, wall time and target attainment for each
  numeric, bounded-program and CPU-kernel workload family.
- **Given** islands, conditional migration, novelty, calibration, growth and
  continuous dispatch, **when** additions/removals and registered interactions
  run, **then** preserve every outcome and produce 54 paired baseline comparisons
  from the complete 19-configuration matrix. A removal of islands also removes
  migration; it is explicitly a joint effect.
- **Given** a development nominee, **when** independent confirmation runs,
  **then** use frozen new tasks/seeds and multiplicity-adjusted bounds. A nominee
  that does not clear the registered minimum gain cannot replace the baseline.
- **Given** altered raw observations, final elites, reference cells, costs,
  analysis source or request identity, **when** evidence is validated, **then**
  reject it. Failed/censored runs stay in the denominators.

## Implemented and verified

Protocol v2 reuses the original experiment machinery but introduces new task
definitions and seed ranges. It pins the analysis source as well as executable
identities; regenerating only the report under changed criteria is refused.
Final quality and diversity are reconstructed from raw-observation-bound elites.
Kernel timings require finite positive observations. Target misses remain null;
the aggregate includes reach rate and budget+1 penalized calls, not a zero cost.

The full registered study completed **7,968 runs / 509,952 evaluator calls /
zero failed runs**: 32 development seeds and 512 confirmation seeds, 64 calls per
run. No model calls or external competitor experiments were used. The confirmation
radius is about 0.1265, versus 0.506 with the old 32-seed pilot. Sample size was
fixed before execution; no retrospective narrowing or optional stopping occurred.

Final verification: clean Release build (zero warnings/errors), 721 net10 + 658
net8 + 658 net471 tests, 104 Python analysis tests, and formatting all pass with
zero skips. The initial nullable-quality compilation error and its corrected
build are retained. Unchanged US-06 sandbox evidence remains on the dependency.

## Measured results

Development means, before (Uniform baseline) → after (nominated configuration):

| Family / nominee | Quality | Reference diversity | Target success | CPU ms/run | Wall ms/run |
| --- | ---: | ---: | ---: | ---: | ---: |
| Numeric / Ratio | 0.7935 → 0.8748 | 0.3208 → 0.2803 | 37.5% → 71.9% | 16.113 → 17.578 | 9.070 → 10.642 |
| Bounded program / all | 0.9198 → 0.9324 | 0.3364 → 0.4932 | 96.9% → 100% | 20.508 → 27.832 | 10.623 → 12.902 |
| CPU kernel / growth | 0.9462 → 0.9460 | 0.2412 → 0.5112 | 100% → 100% | 40.039 → 45.898 | 22.829 → 21.849 |

Numeric penalized calls to reach the target fall from 55.406 to 41.500. These are
descriptive development effects, not proven production gains. In particular,
the kernel nomination is driven by diversity, **not** improved best kernel quality.

| Independent confirmation | Mean paired endpoint gain | Simultaneous lower gain | Decision |
| --- | ---: | ---: | --- |
| Numeric / Ratio | +0.04744 | -0.07903 | Retain baseline |
| Bounded program / all | +0.04494 | -0.08153 | Retain baseline |
| CPU kernel / growth | +0.06709 | -0.05937 | Retain baseline |

The endpoint is the preregistered 0.75×quality + 0.25×diversity; required lower
gain is greater than 0.02. All three nominees remain inconclusive. Generated
presets retain baseline; no library defaults are changed or declared optimal.
Bounds assume independent bounded seed replicates; timing/system drift is not
eliminated by randomized order. Repeated kernel searches are not distinct tasks.

## Scope and handoff

The program workload is a trusted two-node expression grammar executing 2,048
inputs per evaluation, not unrestricted LLM-generated source. Kernel candidates
are correctness-checked 24×24 CPU implementations. Presets apply to these explicit
local workloads; they are not claims about model-driven programs, production
kernels or superiority over OpenEvolve. That comparison is a separate US-02 gate.
